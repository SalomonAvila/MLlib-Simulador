Objetivos y contexto

Qué busca este simulador y por qué importa en HPC.

Objetivo general

Comprender, mediante un simulador interactivo, cómo Spark MLlib entrena árboles de decisión de forma distribuida y cómo el costo del entrenamiento responde a la carga de datos y a la configuración del algoritmo y del clúster.

Objetivos específicos

  1. Explicar los fundamentos del algoritmo: impureza (Gini, entropía, varianza), ganancia de información, candidatos de split por bins y reglas de parada.
  2. Experimentar con los parámetros de MLlib (maxDepth, maxBins, minInstancesPerNode, minInfoGain…) y observar su efecto en el árbol y en el error de prueba.
  3. Analizar cómo escalan el cómputo y la comunicación con las instancias, las features, maxBins, maxMemoryInMB y el número de ejecutores.
  4. Relacionar el entrenamiento con conceptos de HPC: paralelismo de datos, agregación distribuida, costo de red frente a cómputo y memoria como restricción.

Contexto

Cuando los datos no caben o no se procesan a tiempo en una sola máquina, el entrenamiento de modelos se vuelve un problema de computación de alto rendimiento. Apache Spark reparte el trabajo entre ejecutores de un clúster, y su biblioteca MLlib incluye árboles de decisión que particionan los datos por filas para entrenar de forma distribuida con millones de instancias.

En cada pasada sobre los datos, cada ejecutor calcula estadísticas parciales de sus filas (por nodo, feature y bin); esas estadísticas se agregan por la red y con ellas se elige el mejor split. Por eso el tiempo de entrenamiento depende del equilibrio entre cómputo (lineal en instancias, features y maxBins) y comunicación (lineal en features y maxBins), y de cuántos nodos caben en memoria por pasada.

Este simulador usa la API basada en RDD (spark.mllib). En Spark, esa API está en modo mantenimiento y la API principal de machine learning es spark.ml, basada en DataFrames; los conceptos del algoritmo son los mismos.

Cómo usar el simulador

  1. Didáctica y conceptual: lee la teoría (según la guía oficial) y practica con la calculadora de impureza, la ganancia de información paso a paso y el quiz.
  2. Simulador frente a carga → Simulador 3D: elige un dataset, ajusta los parámetros y observa cómo crece el árbol; haz clic en el plano para predecir un punto.
  3. Simulador frente a carga → Carga del clúster: cambia el tamaño de los datos y del clúster, ejecuta la simulación y compara las curvas de escalamiento.

Alcance y limitaciones

  • El Simulador 3D entrena de verdad en el navegador, replicando el algoritmo de MLlib (bins por cuantiles, ganancia de información y reglas de parada), pero en una sola máquina y con datos de 2 features.
  • La carga del clúster usa un modelo de costos didáctico: sus constantes son ilustrativas y sirven para comparar configuraciones, no para predecir el tiempo de un clúster real.
  • Las features categóricas se explican en la parte conceptual y didáctica; los datasets del simulador solo tienen features continuas.

Árboles de decisión en spark.mllib

Los árboles de decisión y sus ensambles son métodos populares para las tareas de clasificación y regresión. Se usan ampliamente porque son fáciles de interpretar, manejan features categóricas, se extienden a clasificación multiclase, no requieren escalar las features y capturan no linealidades e interacciones entre features. Los ensambles de árboles, como random forests y boosting, están entre los mejores métodos para clasificación y regresión.

spark.mllib soporta árboles de decisión para clasificación binaria y multiclase y para regresión, con features continuas y categóricas. La implementación particiona los datos por filas, lo que permite entrenamiento distribuido con millones de instancias.

Los ensambles (Random Forests y Gradient-Boosted Trees) se describen en la guía de Ensembles.

Algoritmo básico

El árbol de decisión es un algoritmo voraz que realiza un particionamiento binario recursivo del espacio de features. El árbol predice la misma etiqueta para cada partición inferior (hoja). Cada partición se elige de forma voraz seleccionando el mejor split de un conjunto de splits posibles, para maximizar la ganancia de información en el nodo. Es decir, el split de cada nodo se elige del conjunto

argmaxs IG(D, s)

donde IG(D, s) es la ganancia de información al aplicar el split s al conjunto de datos D.

Impureza del nodo y ganancia de información

La impureza del nodo mide la homogeneidad de las etiquetas en el nodo. La implementación ofrece dos medidas para clasificación (impureza de Gini y entropía) y una para regresión (varianza).

ImpurezaTareaFórmulaDescripción
giniClasificaciónΣi=1..C fi(1 − fi)fi es la frecuencia de la etiqueta i en el nodo y C es el número de etiquetas únicas.
entropyClasificaciónΣi=1..C −fi log(fi)fi es la frecuencia de la etiqueta i en el nodo y C es el número de etiquetas únicas.
varianceRegresión(1/N) Σi=1..N (yi − μ)2yi es la etiqueta de una instancia, N el número de instancias y μ la media, μ = (1/N) Σi=1..N yi.

La ganancia de información es la diferencia entre la impureza del nodo padre y la suma ponderada de las impurezas de los dos nodos hijos. Si un split s divide el conjunto D de tamaño N en Dizq y Dder, de tamaños Nizq y Nder:

IG(D,s) = Impureza(D) − Nizq⁄N·Impureza(Dizq) − Nder⁄N·Impureza(Dder)

Candidatos de split · features continuas

En datasets pequeños, en implementaciones de una sola máquina, los candidatos de split de cada feature continua suelen ser sus valores únicos. Algunas implementaciones ordenan los valores y usan los valores únicos ordenados como candidatos para acelerar el cálculo.

Ordenar es costoso en datasets grandes y distribuidos. Esta implementación calcula un conjunto aproximado de candidatos mediante un cálculo de cuantiles sobre una fracción muestreada de los datos. Los splits ordenados crean bins, y su número máximo se especifica con el parámetro maxBins.

El número de bins no puede ser mayor que el número de instancias N (escenario raro, pues el valor por defecto de maxBins es 32). El algoritmo reduce automáticamente los bins si no se cumple esta condición.

Candidatos de split · features categóricas

Para una feature categórica con M valores posibles (categorías) habría 2M−1−1 candidatos. En clasificación binaria (0/1) y regresión se reducen a M−1 ordenando las categorías por la etiqueta promedio (ver la sección 9.2.4 de Elements of Statistical Learning).

Ejemplo: clasificación binaria con una feature categórica de categorías A, B y C, cuyas proporciones de etiqueta 1 son 0.2, 0.6 y 0.4. Las categorías se ordenan como A, C, B y los dos candidatos son A | C, B y A, C | B, donde «|» indica el split.

En multiclase se usan las 2M−1−1 particiones siempre que es posible. Cuando 2M−1−1 es mayor que maxBins, se usa un método (heurístico) similar: las M categorías se ordenan por impureza y se consideran los M−1 candidatos resultantes.

Regla de parada

La construcción recursiva del árbol se detiene en un nodo cuando se cumple alguna de estas condiciones:

  1. La profundidad del nodo es igual al parámetro de entrenamiento maxDepth.
  2. Ningún candidato de split produce una ganancia de información mayor que minInfoGain.
  3. Ningún candidato de split produce nodos hijos que tengan cada uno al menos minInstancesPerNode instancias de entrenamiento.

Consejos de uso · especificación del problema

Los parámetros se listan aproximadamente en orden de importancia descendente. Quien empieza debería considerar sobre todo esta sección y el parámetro maxDepth. Estos parámetros describen el problema y el dataset: deben especificarse y no requieren ajuste.

  • algo: tipo de árbol, Classification o Regression.
  • numClasses: número de clases (solo clasificación).
  • categoricalFeaturesInfo: qué features son categóricas y cuántos valores puede tomar cada una, como un mapa de índice de feature → aridad. Las features fuera del mapa se tratan como continuas. Ej.: Map(0 -> 2, 4 -> 10) indica que la feature 0 es binaria (0 o 1) y que la 4 tiene 10 categorías ({0, 1, …, 9}). Los índices empiezan en 0.

No es obligatorio especificar categoricalFeaturesInfo: el algoritmo corre igual y puede dar resultados razonables, pero el desempeño debería ser mejor si las features categóricas se designan correctamente.

Criterios de parada y parámetros ajustables

Al ajustar estos parámetros, valida sobre datos de prueba separados para evitar el sobreajuste. Los valores por defecto son los de DecisionTree.trainClassifier / trainRegressor en Python.

ParámetroGrupoDescripciónPor defecto
maxDepthParadaProfundidad máxima del árbol. Los árboles más profundos son más expresivos (potencialmente más precisos), pero más costosos de entrenar y más propensos al sobreajuste.5
minInstancesPerNodeParadaPara dividir un nodo, cada hijo debe recibir al menos este número de instancias de entrenamiento. Se usa comúnmente con RandomForest, que suele entrenarse más profundo que los árboles individuales.1
minInfoGainParadaPara dividir un nodo, el split debe mejorar al menos esta cantidad (en ganancia de información).0.0
maxBinsAjustableNúmero de bins al discretizar features continuas. Aumentarlo permite considerar más candidatos y splits más finos, pero incrementa el cómputo y la comunicación. Debe ser al menos el número máximo de categorías M de cualquier feature categórica.32
maxMemoryInMBAjustableMemoria para recolectar estadísticas suficientes. Aumentarlo puede acelerar el entrenamiento (si hay memoria) al permitir menos pasadas sobre los datos, con rendimientos decrecientes porque la comunicación de cada iteración puede ser proporcional a maxMemoryInMB.
Detalle de implementación: el algoritmo recolecta estadísticas de grupos de nodos a dividir (no un nodo a la vez). Cuántos nodos caben en un grupo depende de los requisitos de memoria (que varían según las features); maxMemoryInMB es el límite que cada worker puede usar para estas estadísticas.		256 MiB
subsamplingRateAjustableFracción de los datos de entrenamiento usada para aprender el árbol. Es más relevante para ensambles (RandomForest y GradientBoostedTrees); para un solo árbol es menos útil, pues el número de instancias no suele ser la restricción principal.1.0
impurityAjustableMedida de impureza usada para elegir entre candidatos de split. Debe coincidir con algo.gini / variance

Caché y checkpointing

MLlib 1.2 agregó funciones para escalar a árboles más grandes (profundos) y a ensambles. Con maxDepth grande puede ser útil activar la caché de ids de nodo y el checkpointing (también con RandomForest cuando numTrees es grande).

  • useNodeIdCache: si es true, el algoritmo evita enviar el modelo actual (árbol o árboles) a los ejecutores en cada iteración. Útil con árboles profundos (acelera el cómputo en los workers) y con Random Forests grandes (reduce la comunicación por iteración). Por defecto, el modelo se comunica a los ejecutores para que asocien cada instancia con su nodo; con esta opción, esa información se guarda en caché.
  • checkpointDir: directorio para el checkpoint de los RDD de la caché de ids de nodo.
  • checkpointInterval: frecuencia del checkpoint. Muy baja ⇒ overhead extra por escrituras a HDFS; muy alta ⇒ problemas si fallan ejecutores y hay que recomputar el RDD.

La caché genera una secuencia de RDD (uno por iteración); ese linaje largo puede causar problemas de desempeño, que el checkpointing de RDD intermedios alivia. El checkpointing solo aplica cuando useNodeIdCache es true.

Escalamiento

  • El cómputo escala aproximadamente de forma lineal en el número de instancias de entrenamiento, en el número de features y en maxBins.
  • La comunicación escala aproximadamente de forma lineal en el número de features y en maxBins.
  • El algoritmo lee datos dispersos (sparse) y densos, pero no está optimizado para entradas dispersas.

④ Entrenamiento por grupos de nodos (pseudocódigo)


función entrenar(D, params):
  bins ← cuantilesAproximados(muestra(D), maxBins)
  cola ← [raíz(id=1)]
  mientras cola ≠ ∅:
    grupo ← tomarNodos(cola, maxMemoryInMB)   // límite de memoria
    // 1 pasada distribuida sobre D (por particiones)
    stats ← D.mapPartitions(agregarPorNodoFeatureBin)
             .reduceByKey(sumar)
    para nodo en grupo:
      s* ← argmaxs IG(nodo, s)  // prefijos sobre bins
      si depth = maxDepth o IG(s*) ≤ minInfoGain
         o hijos < minInstancesPerNode:
        nodo.isLeaf ← verdadero
      si no:
        nodo.split ← s*
        encolar(hijo 2·id, hijo 2·id+1)
  retornar modelo

          Supuestos del modelo. Bytes de estadísticas por nodo = features × maxBins × tamaño de stats × 8 (stats = numClasses en clasificación; 3 — conteo, suma, suma² — en regresión). Nodos por pasada = ⌊maxMemoryInMB / bytes por nodo⌋. Cada pasada recorre las N·subsamplingRate instancias; sin useNodeIdCache el modelo actual se envía a los ejecutores y cada instancia se asocia a su nodo recorriendo el árbol desde la raíz (costo ∝ nivel). La agregación tipo treeAggregate envía las estadísticas de cada ejecutor por la red. Las constantes (≈4·10⁷ operaciones/s por núcleo, 80 ms de overhead por job) son ilustrativas: sirven para comparar configuraciones, no para predecir un clúster real.
